# Bridge 静默断链修复（0.5.1）

2026-11-06，北京时间。Bridge 与云中转更新至 0.5.1，Android 保持 0.5.0；协议兼容，无需重装。

## 原因与证据

- 08:04:38，云中转记录 Bridge `connection.heartbeat-expired`，随后关闭连接（1006）。
- 手机到中转的探测仍持续成功，但回复 `online:false`，说明电脑 Bridge 链路缺失。
- 电脑进程继续运行，却没有感知旧 WebSocket 已失效。09:49:07，新任务产生发送后才记录 `relay.closed`，随后重新认证；云端 09:49:10 接入。
- 这是长连接半开且 Bridge 缺少主动失活检测导致的恢复缺陷。最初网络中断原因无法由现有日志确定；未发现可据以认定休眠的系统日志。后台 `DESKTOP_TOOL_TIMEOUT` 单独记录，不能据此认定它是断链根因。

## 修复行为

Bridge 认证后立即发 WebSocket 控制帧 ping，随后每次收到对应 pong 的 15 秒后再发；8 秒没有匹配回复即 terminate 旧连接，沿现有路径在 2 秒后重新连接。不再依赖聊天产生新输出来发现断链。认证阶段另设 10 秒超时。

云中转允许凭据正确且 runtime epoch 相同的新连接替换旧连接，避免旧 TCP 占位阻塞重连；不同运行时仍拒绝占用，错误凭据仍拒绝。重连后重新发送已订阅会话快照，重建中转缓存。日志记录心跳超时、回复耗时和同运行时替换，不输出凭据。

在事件循环正常运行且网络重新可用时，静默故障通常在约 23 秒内被发现，再进入 2 秒重连；这不是网络恢复或电脑休眠情况下的时间保证。

## 验证

- 37 项自动测试通过，包含真实 WebSocket 的空闲心跳、静默对端、错误 pong，以及运行时替换/凭据拒绝；TypeScript 检查与服务打包通过。
- 用生产 Bridge 入口连接本机故障注入服务，服务接收认证但不回复第一条连接的心跳。Bridge 自主强制断开并重新认证，第二条连接恢复正常；发送桌面命令数为 0，没有另起 Codex 进程。
- 云端 systemd 服务运行 0.5.1，电脑启动器拉起 Bridge 0.5.1。公网连续心跳通过，记录 seq=1（62ms）、seq=4（39ms）。
- 在现有 Android 模拟器 emulator-5570 的生产包 com.remoteapp.mobile，从测试聊天输入并发送专用消息，界面经历运行态并收到 BRIDGE_HEARTBEAT_FIX_OK；通过当前桌面同一聊天读取最终状态 completed，内容一致。没有调用工具或修改业务文件。
- 部署时重启 Bridge 改变运行时标识，旧连接占位被中转原有失活检测清除后恢复；没有绕过不同运行时互斥。

未验证边界：用户实体手机的本地日志和此后长期网络稳定性当前不可从环境获取。上述 Android 验收是模拟器，不能视为实体手机验收。
